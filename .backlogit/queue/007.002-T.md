internal/capture: Session.Run(ctx, meeting) drives Meeting.Join FIRST; output initialization (the 007.001-T transcript+MP3 file setup) happens ONLY AFTER Join succeeds, per the product contract (Go-TeamsTranscriptCLI-Architecture.md:202), so a failed admission/navigation leaves NO empty artifacts. After Join succeeds it runs EnableCaptions and CaptureAudio concurrently (errgroup with a derived cancellable ctx) until ctx cancel, then flushes/closes. Cancellation is the session's only normal completion path (no meeting-end detection yet). Behavior varies by phase: Meeting.Join can return a wrapped context error when canceled during admission, while active caption/audio methods return nil after cancel. The session MUST normalize this: a context.Canceled/DeadlineExceeded originating from shutdown cancellation is treated as normal graceful completion (Run returns nil) regardless of phase; only genuine failures propagate. Because browser.CaptionSink has no error return, the sink writes to transcript.Writer.WriteEvent and, on a write error, records the first error into a shared field and cancels the session so capture stops instead of silently losing data; Session.Run returns that first non-context error (or the flush/close error). Tests (fake browser.Meeting): (1) Join-before-output-and-capture ordering; (2) caption events written; (3) write/flush failure propagates + cancels (no false success); (4) cancellation during Join -> graceful nil + teardown; (5) cancellation during active capture -> graceful nil + flush/close teardown; (6) Join FAILURE -> NO output files created (or both partial files cleaned up).
