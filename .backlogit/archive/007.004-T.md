internal/cli: the schedule daemon's cron job runs the same capture.Session flow (browser context + Meeting + session) per configured meeting, reusing the join seam. Daemon-wide overlap invariant: cron.SkipIfStillRunning only serializes repeated runs of ONE entry, so two distinct entries firing at overlapping times would otherwise open concurrent Chromium sessions against the shared single profile (UserDataDir), causing profile-lock contention. Since capture.Session.Run holds the profile until ctx cancel (no meeting-end detection yet), a BLOCKING mutex would deadlock the recurring roster (first meeting holds the gate for the daemon's lifetime). Instead use a NON-BLOCKING daemon-wide profile gate (TryLock/atomic busy flag): when a distinct entry fires while a capture is active, SKIP it and log 'schedule: skipped, profile busy'; do NOT block. Also update the schedule command Long help text: it currently promises meeting-end detection 'arrives with live capture support' — after this shipment adds live capture that is false, so the help must accurately describe the non-blocking busy-skip limitation and that finite meeting-end detection + per-meeting profile isolation (true concurrent capture) remain deferred follow-ups. Tests: (1) cron job wiring with fakes; (2) two overlapping DISTINCT entries -> second is skipped/logged, exactly one capture launch against the shared profile (assert the skip behavior). Scope: schedule.go + schedule tests only.
