1. internal/updater uses only the Go standard library and internal/version (zero new external dependencies in go.mod).
2. Fail-closed lock acquisition with zero automatic eviction of <exe>.lock or <exe>.lock.ctl (Findings 1 & 7, Comment 4543360510): Updater.swap acquires <exe>.lock via acquireSwapLock(ctx, exe) using os.OpenFile(lockPath, os.O_CREATE|os.O_EXCL|os.O_WRONLY, 0o600) (writing and flushing JSON owner metadata {pid, token, created_at}) before removing stale <exe>.old, and releases <exe>.lock only after renaming/rolling back <exe> and removing <exe>.old. While <exe>.lock exists (os.ErrExist), contenders poll every lockPollInterval (default 50ms) up to lockWaitTimeout (default 15s) respecting caller ctx.Done() for acquisition/wait, and NEVER unlink, rename, or replace an existing <exe>.lock or <exe>.lock.ctl (<exe>.lock.ctl fails closed to manual control-lock cleanup and never auto-evicts a .ctl file, so two competing control-lock contenders never steal a live <exe>.lock.ctl). When lockWaitTimeout expires, the contender inspects <exe>.lock metadata (pid, token, created_at), lockStaleAfter (default 2m), and injectable isProcessAlive(pid) for diagnostic classification only in the returned ErrUpdateLocked error: (a) dead-PID / stale lock (now - created_at > lockStaleAfter and !isProcessAlive(pid)) reports that <exe>.lock appears orphaned by dead PID <pid> (age <age>) and states the manual recovery steps; (b) live-PID past stale threshold (now - created_at > lockStaleAfter and isProcessAlive(pid)) reports that <exe>.lock is held by live PID <pid> past lockStaleAfter (explicitly noting that if no teams-cli update process is running, the OS may have reused PID <pid>) and states the manual recovery steps; (c) active / corrupt / unreadable lock reports active contention or unreadable metadata and states the manual recovery steps.
3. Non-cancelable error-returning release under fail-closed <exe>.lock.ctl (Findings 1 & 2, Comment 4543360569): acquireSwapLock(ctx context.Context, exe string) returns (release func() error, err error). While acquisition/wait honors the caller's ctx cancellation, release() derives an independent non-cancelable bounded cleanup context via context.WithTimeout(context.WithoutCancel(ctx), u.ctlLockWaitTimeout) (default 2s, polling at ctlLockPollInterval default 10ms / wall-clock deadline -- never canceled by the caller's ctx) to acquire fail-closed <exe>.lock.ctl (os.OpenFile(lockPath+'.ctl', os.O_CREATE|os.O_EXCL|os.O_WRONLY, 0o600), never auto-evicted) around the authoritative token read + comparison + os.Remove(lockPath) before removing <exe>.lock.ctl (with an injectable test hook between initial unlocked token inspection and <exe>.lock.ctl acquisition so external/test replacement is detected and never unlinked). swap(ctx, exe, tmp) executes relErr := release() and returns errors.Join(swapErr, relErr); if swap succeeded in replacing exe on disk (rename(tmp, exe) succeeded) and only release() returned a cleanup error, Update sets res.Updated = true while still returning the non-nil release() error surfacing the stranded lock (whereas if swap itself failed before replacing exe, Updated remains false).
4. Executable path safety (preserving legitimate .old filenames vs. failing closed on renamed running image), symlink target marker check, immediate os.Stat re-probe, and start-of-Update baseline snapshot + under-lock installedVersion / running-image identity guard when !force (Finding 3, Comments 4543360630, 4543766778, 4543766919, 4543907702): (a) Do NOT unconditionally strip .old in executablePath(). A configured u.cfg.ExecutablePath ending in .old or a process legitimately invoked as <name>.old (filepath.Base(os.Args[0]) ends in .old) MUST preserve its exact .old path and use <exe>.old.lock / <exe>.old.old without ever redirecting to a sibling <exe>. When u.cfg.ExecutablePath == '' and os.Executable() / filepath.EvalSymlinks resolves to a path ending in ' (deleted)' or ending in .old while filepath.Base(os.Args[0]) does NOT end in .old (corroborating that another updater renamed the running executable image after launch), fail closed with ErrConcurrentUpdateModified (reporting that the running binary was already replaced by another update process) unless --force is set with an explicit path. (b) A helper in internal/updater/updater.go used by executablePath() and downloadVerified() resolves any symlink's target path (or parent dir + link target when dangling) so marker checks inspect <target>.lock and <target>.old; if os.Stat(exe) fails with fs.ErrNotExist and neither marker is seen, it performs one immediate re-probe of os.Stat(exe) before returning fs.ErrNotExist (in case the holder finished swap and removed both markers between the initial failed Stat and the marker check); when os.Stat(exe) fails with fs.ErrNotExist while <target>.lock or <target>.old exists, it polls every lockPollInterval up to lockWaitTimeout (respecting ctx.Done()) waiting for the in-flight swap to restore exe (returning ErrUpdateLocked if lockWaitTimeout expires while <target>.lock is still present), without holding <exe>.lock across the network download. (c) Capture the baseline snapshot (os.Stat + SHA-256) at the VERY START of Update (before lookup and before any wait); set concurrentSwapObserved = true ONLY when exe is missing (fs.ErrNotExist) OR <exe>.lock exists on disk at that initial check (so B had to wait for an in-flight swap) and reject !force under <exe>.lock (ErrConcurrentUpdateModified) -- NEVER set concurrentSwapObserved merely because a leftover <exe>.old exists alongside an intact exe when <exe>.lock is absent, because a leftover <exe>.old beside an intact exe with no <exe>.lock is normal post-update steady state on Windows (preserving stale-backup cleanup at the start of swap and TestUpdateReplacesStaleOldFile). In addition, under <exe>.lock inside swap when !force, verify installed-binary version / running-image identity before rename(exe, old) via an injectable installedVersion func(ctx context.Context, exePath string) (string, error) (or running-executable os.SameFile + SHA-256 identity check when u.cfg.ExecutablePath == '') that inspects the on-disk exe under <exe>.lock and rejects the swap with ErrDowngrade / ErrConcurrentUpdateModified if the on-disk binary at exe is already at a version newer than res.LatestVersion (or was replaced since B's running image launched). Manual recovery documentation also specifies that if a crash between rename(exe, old) and rename(tmp, exe) left <exe> missing and <exe>.old present, the operator restores <exe>.old -> <exe> after confirming all teams-cli update processes have exited and before removing <exe>.lock.
5. Concurrent fixture serialization vs. Windows running-image <exe>.old lock behavior (Finding 4): (a) When two concurrent Updater.Update calls target a fixture binary ExecutablePath that is not mapped as a running Windows process image (or on Unix), <exe>.lock serializes them and both updates succeed in sequence without corrupting <exe>.old; (b) when os.Remove(old) at the start of swap fails because <exe>.old is still locked/mapped by a running Windows process (simulated deterministically via an open exclusive file handle or injectable removeOld hook on <exe>.old), swap aborts cleanly at 'remove stale backup <exe>.old' before moving the newly installed exe aside, leaving the first updater's installed binary intact on disk.
